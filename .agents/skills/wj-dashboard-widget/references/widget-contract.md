# Dashboard widget contract

The framework source is in `src/main/webapp/admin/v9/src/js/dashboard/` (paths in this reference are repository-relative). Read `registry.js`, `dashboard.js`, and `model.js` when extending shared behavior.

## Registration

Import `registerWidget` from `./registry` and register each type once. Definitions contain:

- `type`: stable identifier, also allowlisted with its sizes by the settings backend.
- `titleKey`, optional `descriptionKey`: translation keys ending in `.js`; use the `admin.dashboard` namespace.
- `icon`: a Tabler `ti-*` class.
- `sizes`: subset of `1x1`, `2x2`, `2x3`, `3x2`, `3x3`, `fullauto`; `defaultSize` must belong to it.
- `multiple`, `mandatory`: false by default. Mandatory widgets cannot be removed.
- `defaultOptions`, `defaultDomainOptions`: shared and active-domain preferences, respectively.
- `isAvailable(context)`: presentation eligibility; data authorization remains server-side.
- Optional `isVisible(instance, context)` hides acknowledged content without removing the stored instance. A hidden singleton may expose `reveal(instance, context)` so the catalogue can show it again. Do not use this for permission checks or fixed security/release regions.
- Optional `getTitle(instance, context)` for a text-only instance title.
- Optional `headerLink: {href, labelKey?}` for a safe local module link. `href` is a string or `(instance, context) => string`, allowing a selected record's destination to follow current domain settings. Every update is validated by the shared link helper. Without `labelKey` the title becomes a link; with it a separate translated link sits beside the title. Header navigation survives loading, errors and title updates. Use it instead of a duplicate footer link.
- `render(args)`, optional `configure(args)`.

`render` receives `{container, instance, options, domainOptions, context, signal, refresh, saveOptions}`. Append safe DOM nodes to `container`. `context` contains `data`, `labels`, `config`, `overview`, `dashboard`, `settings`, and `translate(key)`. Use `signal` with asynchronous requests. Return a cleanup function or `{destroy()}` when owning resources; asynchronous returns are supported. The framework aborts and cleans up stale renders, shows failures, and provides retry controls.

`configure` receives the same data context and an abort signal, without refresh/save callbacks. Add labeled controls to its container and return `{read: () => ({options, domainOptions}), destroy?}`. Read may reject invalid input with a localized Error. The framework owns the size picker, modal, save/cancel, focus, and atomic persistence.

Use `saveOptions({options, domainOptions})` for an in-widget preference action. It returns a Promise<boolean>; do not display successful persistence until true. Use `refresh()` to reload only this instance.

`context.dashboard.showAddWidget(type)` opens configuration before a new instance is persisted; canceling leaves the profile unchanged. Use this for the shortcut strip add action.

`context.dashboard.showDialog(title)` opens a shared modal and returns `{body, footer, close, signal, setCleanup}`. Bind requests to its signal and let the shared modal restore focus and dispose resources. Active sessions are managed directly in their fixed list and do not need a separate dialog.

## Settings API

Preferences are embedded as `overviewData.settings` by `DashboardListener` and read by `DashboardController.start()`. There is no settings GET endpoint or fallback fetch. Successful saves and resets update the page data so rebuilding the component retains the confirmed state. A domain change loads new bootstrap data with the page. `PUT /admin/rest/dashboard/settings` saves and returns:

```json
{
  "version": 1,
  "configured": true,
  "shortcutsConfigured": true,
  "legacyBookmarksHandled": false,
  "items": [
    {"id": "security", "type": "sessions", "size": "2x3", "options": {}},
    {"id": "stable-id", "type": "shortcut", "size": "1x1", "options": {"source": "menu", "href": "/apps/form/admin/"}}
  ],
  "domainOptions": {"stable-id": {}},
  "acknowledgedNewsVersion": null
}
```

The server derives user and active domain. Never send a user ID or arbitrary domain selector. The server validates allowed types, sizes, singleton rules, identifiers, and storage limits. Shared layout records and active-domain filters are committed together; failed saves leave the confirmed UI state unchanged.

`getDashboardDefaults(context)` defines the explicit, permission-filtered layout for new and reset profiles: traffic `3x3`, forms/approvals/errors `1x1`, recent pages `3x2`, and referrers/publishing/newsletter `2x2`. Newsletter is the final grid widget. Other registered types, including search terms, top pages and system/activity widgets, remain available in the catalogue and are never appended automatically. On the six-column desktop grid the metric row and recent pages align beside traffic, followed by three equal-width previews. Existing recent-page `2x3`/`3x3`, referrer `2x3`/`3x3`, publishing `2x3`, and search-term `2x3` sizes remain valid; the revised defaults never rewrite saved sizes or order. Sessions, news and search render in fixed regions above the personal grid; shortcuts render as wrapping links directly under the greeting inside the welcome panel, before release news. The section has an accessible label but no visible heading. Fixed-region display does not rewrite stored sizes or order. Widget minimization is not supported: old `collapsed` properties are ignored by both the server DTO and client normalization, without discarding the rest of a saved profile. Default shortcuts select authorized pages/forms destinations, falling back to the first authorized menu destination; no placeholder is created when the menu has no destination. Manually added types use their registered default size. New optional widget types must not rewrite existing personal layouts. Mandatory types are ensured separately.

The controller starts in view mode. The toolbar's feedback button opens `context.overview.showFeedbackModal()` before the widget controls; it remains available independently of widget loading. `setEditing(true)` reveals add-widget, reset, movement and settings controls without persistence. The toolbar order is feedback, add widget, reset, then edit/done. `setEditingShortcuts(true)` independently reveals shortcut add/reset/move/settings controls beside the greeting; entering either edit mode closes the other. Shortcuts are absent from the grid catalogue. Shortcut reset replaces only shortcut instances through PUT, preserving widget filters and read news. Removing all shortcuts leaves an intentionally empty section until an explicit shortcut reset. Reset has an explanatory tooltip and uses the standard `WJ.confirm`; the widget catalogue contains no reset control. Successful saves and resets use `WJ.notifySuccess` with a 10-second timeout instead of a persistent inline message. Moving cards stays within the personal grid or shortcut strip; fixed regions cannot be moved. Keyboard/touch movement uses the same region restrictions as drag. Body-level drag helpers retain the source card's dimensions, background, border and inherited dashboard color tokens.

`DELETE /admin/rest/dashboard/settings` takes no body and resets the authenticated user's shared layout, widget options in **all domains**, and news acknowledgement. It uses the same per-user database lock and transaction as PUT, retains ordered shortcut instances plus `shortcutsConfigured` and `legacyBookmarksHandled` metadata from the locked snapshot, returns a `configured:false` DTO only after commit, and clears the account's admin-settings cache. It preserves every non-dashboard preference and browser-local legacy bookmark. A retained `shortcutsConfigured:true` prevents default shortcut recreation, including for an empty saved section. Older saved layouts without this flag are treated as configured; a missing profile is unconfigured. The system confirmation dialog explains this scope before any DELETE request. A failure uses the normal shared error feedback and leaves the toolbar available for retry. On success the controller applies current defaults; they remain unconfigured until the first personal edit. On failure retain the previous layout, filters, news acknowledgement and removal undo. Never implement reset as a sequence of partial PUT requests or by clearing localStorage.

Shift-clicking the widget reset calls `PUT /admin/rest/dashboard/settings/reset` with a generated settings DTO. The client iterates authorized registry definitions and each definition's `sizes`, assigning unique IDs and default shared/domain options. Shortcuts keep their own section and are preserved from the locked account snapshot; a previously unconfigured shortcut strip may use the supplied defaults. Sessions, news and search remain singletons; all grid types allow repeated instances. The reset transaction replaces all old widget and domain records, clears news acknowledgement, and stores a configured layout before returning it. Failure preserves the previous profile. The generated layout survives reload immediately and supports removal, undo and size changes through normal editing. A normal reset returns to the curated default list. The 48-instance limit fits the current full catalogue and keeps a UUID-based order record within the 2000-character storage limit; reject overflow before any mutation, never truncate.

## Data and rendering

`DashboardListener` embeds `settings`, `notices` and `currentSessions` alongside menu/identity data in the existing `overviewData` JSON. It also embeds `loggedAdmins` (distinct user IDs, names and emails from `SessionHolder` and cached users) only with `welcomeShowLoggedAdmins` permission. Keep Thymeleaf JavaScript inlining in `overview.pug` for safe serialization. These values are supplied with the page; they have no read REST endpoints or client fallbacks. Sessions come directly from `SessionClusterService`. A completed logout removes the session from the supplied list and updates the count; remote logout remains pending until cluster synchronization. Reloading the page obtains fresh session and administrator lists. Browser fixtures for initial data must override the HTML bootstrap with `mockDashboardBootstrap` from `helpers/dashboard-browser.js`; REST mocks remain necessary for writes and independently loaded widget projections.

The controller shares one `IntersectionObserver` for pending grid renders. It creates card shells immediately, then invokes `render` only when the card intersects the viewport, with no prefetch margin. Requests and chart initialization belong inside these renderers. Entry removes observation; scrolling away and back does not reload an unchanged card. Refresh, configuration changes and domain changes abort previous work and wait for viewport entry again. Removal and destruction also cancel pending waits. Sessions, news, search and shortcuts render immediately; browsers without `IntersectionObserver` retain immediate rendering. Live monitoring and newsletter keep their existing visibility-aware polling after the first render. Browser tests inspecting every card must scroll them into view before waiting for their content; `src/test/webapp/helpers/dashboard-browser.js` provides the shared helpers.

`widget-utils.js` provides safe DOM, URL, field, table, formatting, and fetch helpers. Do not use arbitrary options as HTML or icon classes. Shortcut options are `{source: "menu" | "url", href, title, icon, color}`. Optional `icon` is a single Tabler `ti-*` class (at most 80 characters); an empty or absent value inherits the authorized menu icon or uses `ti-link` for custom URLs. Tabs inherit the nearest parent icon when they have none. Selecting a new destination fills the editable icon field; reopening preserves an override. The field accepts bare names or `ti-*`, previews the result, and persists the normalized class. Optional `color` is one of `default`, `mint`, `lavender`, `blue`, `amber`, `peach`, or `rose`, mapped only to existing dashboard palette tokens. Missing colors keep the default surface. Both options are validated on the server; arbitrary classes and CSS values are rejected. Omitted `source` preserves legacy menu behavior; menu destinations must resolve against the current authorized menu. Explicit URL mode requires a nonempty title and validates a maximum 1024-character root-relative or HTTP(S) URL, rejecting credentials, backslashes, controls and protocol-relative forms. Link titles are always text. `shortcutUrl` mirrors server validation before persistence. The shortcut dialog derives cascading main-area, section and tab selects from the authorized menu tree. Omit empty/unsafe groups, deduplicate a parent URL repeated by its tab, reset dependent choices on a parent change, and preselect the full path when editing. A section with one destination needs no extra tab selection. Missing saved targets require a new explicit choice rather than silently selecting a different URL. Only the selected URL, source, custom title and appearance choices are persisted; menu hierarchy is presentation data. Color choices are labeled native radios with a check mark, keyboard focus and a live shortcut preview.

Dynamic settings use `WJ.initSelectPicker(root, overrides)` from the same shared initializer called by `app-init.js`. It respects `.no-picker` and `data-live-search`, refreshes existing instances after dependent options change, and keeps dropdowns inside their modal for search focus. Fields use explicit label/input IDs so generated picker buttons are not nested in labels. Dialog cleanup destroys pickers and their detached menus; Escape closes an open picker before closing its modal.

Ranked search-term and top-page previews share the default `3x3` size and header navigation, with no duplicate footer link. The table helper accepts an optional zero-based `numericColumns` array to mark both headers and cells with `md-dashboard-widget__table-number`; keep these columns narrow, right-aligned and unwrapped, reserving room for full text in the remaining columns. Ranked tables use automatic column layout and preserve the compact `2x3` variants. Top-page previews use three columns in both sizes: a shared `pagePreview` link with thumbnail, title and parent path; right-aligned count; and change. Their numeric cells are vertically centered. Recent pages reuse the same preview helper, retaining their editor destinations and date labels; top pages retain the statistics detail destination and period query. The top-page provider projects sanitized `perexImage` values for the authorized ranked IDs in one bounded query on its existing connection, rather than reading each full document. Missing or failed thumbnails use the decorative file icon.

Reuse existing module REST endpoints when available; the remaining dashboard projections use `/admin/rest/dashboard/data/{type}` and recent pages use `/admin/rest/web-pages/all` with the configured `systemPagesRecentPages` ID, `size=6`, `page=0`, and `sort=dateCreated,desc`. Request only the widget's necessary projection with its abort signal. Every `/admin/rest/` fetch, including GET, must send `X-CSRF-Token: window.csrfToken`: the repository PathFilter enforces this independently of the HTTP method. jQuery's global AJAX setup does not apply to fetch. Return empty states for successful empty results and let actual failures reach the framework. Never convert an access error to a zero count.

The pilot registrations are in `src/main/webapp/admin/v9/src/js/dashboard/widgets.js`: `shortcut` demonstrates authorized menu/custom URL selection, safe links and shared options; `recent-pages` demonstrates `3x2`, `2x3`, and `3x3` previews, the abortable Web pages module endpoint and 38-pixel local perex thumbnails through `/thumb` with `w=76&h=76&ip=6`, lazy loading and a file-icon fallback. Every size retains up to six pages. The labeled, keyboard-focusable list scrolls natively when its content exceeds the available card height. `containNativeScroll(list, signal)` in `widget-utils.js` keeps wheel, touch and navigation-key events from reaching the administration's smooth scrollbar while the list overflows; it preserves native browser behavior and removes its listeners on abort. Sessions and logged administrators use the same helper; the administrator list retains all active names and email actions. Recent pages read the module response's `content` array and render `fullPath`, `perexImage` and the `dateCreated` timestamp directly. Use `fetchJson` so HTTP-200 DataTable errors remain failures. Search previews still retain their localized `saveDate` strings verbatim. Their behavior tests are in `src/test/webapp/helpers/dashboard-widgets.test.js`.

Build request parameters explicitly from allowed fields. Shared `options.days` describes the period; a record selection such as `domainOptions.formName` is domain-specific and takes precedence over any similarly named shared value. If a stored selection is no longer accessible, retain its preference and show an unavailable state; do not silently select the first record or clear the user's selection.

When adding a type, update frontend registration, backend settings validation, translations, relevant data authorization, tests, and this reference where a new reusable pattern is introduced. Add an example link only after the referenced implementation exists.

## Projection examples and errors

The provider is `src/main/java/sk/iway/iwcm/components/welcome/DashboardWidgetDataService.java`, routed by `DashboardWidgetDataRestController`. Allowed query parameters include `days` (7, 30, or 90), traffic `metric` (`sessions`, `views`, or `uniqueUsers`), and optional `formName` or positive `campaignId` domain selections. Do not pass layout IDs or client domain IDs as authorization context.

For example, `fetchData("forms", {days: 7, formName: domainOptions.formName}, signal)` returns:

```json
{
  "total": 1,
  "from": 1789776000000,
  "to": 1790380799999,
  "items": [{"id": "42", "title": "Contact", "date": 1790000000000, "url": "/apps/form/admin/detail/?formName=Contact"}],
  "options": [{"id": "Contact", "title": "Contact"}]
}
```

`from`/`to` and item dates are epoch milliseconds; display the returned inclusive interval. `items` is a bounded preview; `total` counts the whole authorized result. Form `options` are the authorized form choices. Load unfiltered form options for the settings dialog and retain a missing saved choice with an unavailable label. Actual submissions use their real submission dates; they have no fabricated unread/processed state. Form periods include today so new submissions are immediately visible; the completed-day rule belongs to analytics widgets. The forms provider loads authorized form names through the existing `FormsServiceImpl.getFormsList(user)` service, sharing form administration's definition and permission rules. It queries submissions through `FormsRepository`, filtering by those names, the server-derived tenant ID, the selected period, and the current domain's editable pages. Do not duplicate form discovery or authorization with custom SQL or additional `FormDB` methods.

Approvals fetch the existing `/admin/rest/webpages/toapprove/all` and `/admin/rest/groups/toapprove/all` endpoints with `size=6`, `page=0`, and `sort=saveDate,desc`. Sum `totalElements`, merge by `saveDate`, and retain six entries. Reuse each endpoint's authorization and scope; HTTP 403 and the existing DataTable HTTP-200 errors `Access Denied` / `Access is denied` are permission errors, never empty queues. Reject other nonempty DataTable `error` responses as failures too. The page DataTable response swaps IDs: `historyId` is the page ID and `docId` is the pending history ID. Link directly to `approve.jsp` or `approve_delete.jsp`, including the legacy `[DELETE]` title fallback. Group responses use `GroupSchedulerDetails` and expose `groupId`, `schedulerId`, `isDelete`, `saveDate`, and `userFullName`; link to `web-pages-list/?groupid=...&scheduleId=...`, adding `&act=delete` for deletions, as in approval emails. Prepend the shared `ti-file-text` icon for pages and `ti-folder` for folders. Each item opens a new window with `target="_blank"` and `rel="noopener"`. The header and count retain the complete approval list. For folder-only deep links, defer the folder-tab click until the shared subtab handler has updated its IDs.

Traffic adds `previous`, `series`, and `previousSeries`, each point containing `date` and `value`. Previous points retain their real dates and align by index for chart comparison. Unique visitors are distinct across the full period, never a sum of daily unique counts. A zero comparison baseline has no percentage growth. The 404 provider labels its whole-week coverage; historical data that cannot distinguish domain or year is unavailable rather than a misleading zero.

Charts use `src/main/webapp/admin/v9/src/js/dashboard/charts.js`: create a uniquely identified host with `chartHost`, then call `mountChart` with the render signal and a factory for `ChartTools.LineChartForm` or `BarChartForm`. The helper loads the existing bundle with `window.initAmcharts()`, creates the chart through `ChartTools.createAmchart`, and returns paired `ChartTools.destroyChart` cleanup. Pass that cleanup back from the widget renderer. Do not reuse a host ID across asynchronous renders or keep an AmCharts root after abort. `data-widgets.js` demonstrates equal-period lines with real dates retained in tooltips and period labels in the legend. Traffic and referrers keep their precise-value tables visually hidden for screen readers, without a visible data disclosure. Referrers use horizontal AmCharts percentage tracks on a fixed 0–100 scale with each literal source label and percentage above its track; counts remain available in tooltips and the equivalent table. Shares use the provider's complete total, not the sum of the displayed preview. The `2x2` preview shows three sources, larger variants five or six. It does not invent search/direct categories from the recorded source domains. Dashboard previews omit the full-report scrollbars and zoom controls; the existing WebJET theme and locale remain shared with other modules. `charts.js` reads `--wj-dashboard-chart-primary`, `--wj-dashboard-chart-comparison`, `--wj-dashboard-chart-grid` and `--wj-dashboard-chart-label` from the chart host at creation. Define their colors as SASS tokens exported to CSS custom properties, without hard-coded JavaScript palettes.

Publishing reads the same `DocDB.getPublicableDocs()` cache as the audit awaiting-publication module, applies current-domain and page-access checks, and returns the next six future publish/expire events sorted by event date. Only publicable `DocHistory` entries create publish events; expiry requires `disableAfterEnd`. Duplicate page/kind/date events are removed before counting. There is no 30-day upper bound: the projection returns `from` and omits `to`. Compact `2x2` cards show two events and the legacy `2x3` variant five, with action labels distinguishing publication from expiry. Dates include the year when it differs from the current year. The linked title opens `/admin/v9/apps/audit-awaiting-publish-webpages/` for users with `cmp_adminlog`, otherwise the webpage list; individual events link to their page.

Newsletter returns campaign `options`, `selectedId`, `active`, and items with `status`, `sent`, `recipients`, `failed`, `opens`, and `clicks`. The selected campaign is first. Automatic selection prioritizes an active campaign, the next scheduled campaign, then the last completed campaign. Only an active, visible card polls. The implementation in `data-widgets.js` demonstrates an IntersectionObserver and timer with paired cleanup.

The provider uses 400 for invalid parameters, 403 for denied module access, 404 for unavailable record selections, and 503 for unavailable data. `fetchData` converts JSON `reason` into `error.dashboardReason`, which the shell translates. In particular, `domain-unavailable` and `period-unavailable` explain limitations of historical 404 records. Do not catch provider errors and return an empty array or zero.

`utility-widgets.js` demonstrates mandatory session management, version-specific announcement acknowledgement, and explicit search scope. Session removal must inspect the endpoint's `success` result as well as HTTP status; a 200 response can still report failure. A successful response with `pending: true` means the verified remote session is awaiting cluster synchronization; show that state instead of claiming immediate logout. The current session remains first in the compact preview and cannot be removed through this endpoint. Its fixed header region shows the localized "My active sessions" title and a non-interactive count badge. The list retains every active session and direct logout controls, including profiles with a previously collapsed session widget. A bounded scroll area in this security region preserves access to longer session lists.

Release announcements arrive through WebJET's Markdown renderer, which may represent paragraph boundaries as `<br><br>`. Preserve its complete HTML in the expanded release, including all paragraphs and formatting; extract plain text only for the release version and collapsed teaser. The labeled collapse control shares a footer with the complete changelog link. Acknowledgment of its version collapses it to a visible one-line summary and a more-info toggle, rather than hiding the release. An updated version expands again. Preserve the last confirmed presentation if acknowledgment fails.

## System and activity widgets

`system-widgets.js` registers `changed-pages`, `audit`, `logged-admins`, `server-memory`, and `server-cpu`. They replace the removed legacy overview; shortcuts replace the old browser-local bookmark UI. The legacy `{name, path}` array is stored under `localStorage["bookmarks"]`, so no database migration is needed. After successfully loading the profile, the controller automatically imports a nonempty legacy array once into the signed-in account. It replaces only shortcut instances, preserving safe URLs (including query strings and fragments), names and order while deduplicating URLs. Other widgets, domain filters and news acknowledgement remain unchanged. Only a successful server save records `legacyBookmarksHandled`; the legacy key is then removed if its raw value has not changed during the request. Invalid records, save failures and capacity limits retain both original bookmarks and current preferences without a partial import; loading again retries. Missing or empty legacy lists leave defaults intact. The account marker prevents another overwrite even if localStorage cleanup is unavailable or another browser has old bookmarks. These widget types are optional and support multiple instances and existing personal grid layouts remain unchanged.

Changed pages and audit request their authorized projection from `/admin/rest/dashboard/data/{type}`. Logged administrators use the permission-filtered `overviewData.loggedAdmins` list supplied with the page. The monitoring widgets use the existing `/admin/rest/monitoring/actual` endpoint. Changed pages require `menuWebpages` and apply current-domain and page-access checks. Audit requires `cmp_adminlog`, logged administrators `welcomeShowLoggedAdmins`, and both monitoring widgets `cmp_server_monitoring`. These last four projections describe server-wide activity, like the corresponding administration modules. They must not be presented as active-domain metrics.

Both monitoring widgets default to `3x3`, retaining `3x2` as a compact option. Their larger variant increases the actual chart height on desktop and mobile, while memory uses the shared lavender surface and CPU the mint surface. Time-axis tooltips must remain within the rendering surface, including after scrolling. Monitoring uses current server snapshots from `/admin/rest/monitoring/actual`, independent of historical monitoring configuration. A shared request every 5 seconds supplies both visible widgets without overlapping requests. Each chart retains a bounded collection of real samples observed since its render; update its existing AmCharts series, summary values, sample time (including seconds), and accessible table together. Pause polling while the document or widget is hidden and release subscribers, timers, requests and chart roots on abort, resizing, removal or refresh. Do not fill a live graph with fabricated or persisted historical samples. Initial and subsequent request failures must remain distinguishable from current valid readings. Use the shared chart lifecycle helper and retain the link to full server monitoring.

## Persistence and verification

`DashboardSettingsService` validates the schema and `DashboardSettingsRepository` writes the existing `user_settings_admin` table atomically. The MariaDB/MySQL table must use InnoDB; the targeted migration is in `src/main/webapp/WEB-INF/sql/autoupdate-webjet9.xml`. Do not bypass the repository guard or introduce a separate preference store. The REST DTO uses ordinary maps/lists, compatible with the application's Jackson 3 response converter.

The shared records are `overview.layout.v1`, `overview.widget.<id>`, and `overview.news`; domain records are `overview.domain.<rootGroupId>.<id>`. Immediate removal undo retains the removed instance's other-domain selections until the next successful edit. A failed save must retain the undo opportunity. Unavailable widget types remain in the stored profile.

Run the frontend framework and widget behavior tests (`src/test/webapp/helpers/dashboard-*.test.js`), relevant `Dashboard*Test` Java tests, and the Codecept scenarios in `src/test/webapp/tests/admin/dashboard-widgets.js`, `src/test/webapp/tests/admin/dashboard-data.js`, and `src/test/webapp/tests/admin/dashboard-catalogue.js`. Match verification to the changed provider, permissions, variants, and resource lifecycle. The data scenarios are read-only; the interaction scenarios restore the test account's effective settings. Test security operations only against sessions created by the test. Never invoke the feedback email scenario as part of a dashboard smoke test.

The real reset scenario in `src/test/webapp/tests/admin/dashboard-reset.js` creates and removes a disposable account. Do not run a destructive reset on an existing account whose other-domain preferences cannot be restored through the active-domain API. The catalogue tests inspect AmCharts root registration after refresh, size change, removal, and undo; browser assertions also check chart canvas rendering and the table equivalent.
